- (constraint) [ADOPTED] Agentes de IA no Paperclip (adapter Claude Code) chamam API REST simples direto via curl durante a execução — não mantêm sessão MCP/JSON-RPC entre chamadas. - (constraint) [ADOPTED] Anexar arquivo (HTML) numa issue do Paperclip é um mecanismo instável (2 falhas observadas: agente gera o arquivo mas não consegue anexar de fato, fica em /tmp efêmero). Entrega de relatório/painel pro usuário final deve ser por e-mail (SMTP), gerado server-side, nunca dependendo do agente de IA gerar+anexar HTML.

- (decision) AD-1 [paradigm]: BFF-for-Agents (Backend-for-Frontend, mas o 'frontend' é o agente de IA) — cada módulo FB_* dono do seu domínio expõe SEU PRÓPRIO facade HTTP read-only pros agentes (endpoints /api/<modulo>-jc/*), separado da API interna do módulo pro seu próprio frontend humano. Nenhum módulo implementa lógica de cálculo de OUTRO módulo.
- (decision) AD-2: cerebro-jc-api é promovido a GATEWAY de agregação entre módulos — ponto único que o agente de monitoramento do CEO José Costa (e outros agentes) chama, em vez de um endpoint por módulo. Renomear repositório/serviço pra refletir esse papel (FB_CEREBRO), não fica associado a um módulo específico.
- (decision) AD-3: o Gateway (FB_CEREBRO) SÓ pode ler dado de outro módulo via a API HTTP daquele módulo (o mesmo facade do AD-1) — nunca acesso direto ao banco de um módulo que não seja o dele. Acesso direto a Postgres hoje existente em cerebro-jc-api (Cobertura, Faturado, lendo direto do banco do Farol) é DÍVIDA TÉCNICA herdada, mantida nesta rodada só por não quebrar o que já funciona, migração registrada em Deferred — mas todo código NOVO (Objetivos por Indústria) já segue a regra: proxy HTTP pro endpoint que o FB_FAROL já expõe, nunca reimplementando o cálculo.
- (decision) AD-4: convenção de período em qualquer endpoint agent-facing de qualquer módulo: aceita 'AAAA-MM' OU 'DD/MM/AAAA a DD/MM/AAAA' — mesmo parser já validado em FB_FAROL (parsePeriodo). Novo módulo não inventa formato de data próprio.
- (decision) AD-5: envelope de resposta JSON em snake_case (cod_fornec, venda_atual, etc.) e erro sempre {"error": "mensagem"} com status HTTP apropriado (400 validação, 401 auth, 500 interno) — convenção já em uso nos dois serviços existentes, ratificada como regra de plataforma.
- (decision) AD-6: entrega de painel por e-mail é sempre gerada e enviada SERVER-SIDE pelo módulo dono do dado (nunca pelo agente de IA gerando/anexando HTML) — mesma conta SMTP (Hostinger, credenciais já em uso) reaproveitada por todos os módulos via env vars (SMTP_HOST/PORT/USER/PASSWORD/FROM), mas CADA módulo implementa seu próprio pequeno sender (sem lib compartilhada entre repos/linguagens) — duplicar ~30 linhas de glue é mais barato que acoplar repos possivelmente em linguagens diferentes (FB_COMPRAS pode não ser Go).
- (decision) AD-7 [ADOPTED]: CI/CD de todo módulo/gateway = git push pro branch main → Coolify redeploy automático (mesmo pipeline já em produção pro FB_FAROL) — nunca build/deploy manual via docker build direto no host de produção. cerebro-jc-api hoje viola isso (buildado manualmente em /opt/cerebro-jc sem git) — corrigir nesta rodada é o objetivo imediato.
